# Breeze 0.5

A native macOS app for Apple silicon cooling, personal storage review, and network monitoring. SwiftUI, menu bar controls, and no third-party dependencies. Requires macOS 14 or later.

## Cooling workspace & Liquid Glass

The floating sidebar and navigation cards use native Liquid Glass on macOS 26 and later, with standard materials on macOS 14–15. Action buttons share one Breeze style across screens and sheets, with consistent sizing, neutral supporting actions and mint primary actions. The window blends with the desktop through an AppKit behind-window material, and the sidebar uses native list selection and keyboard navigation. Data panels across Cooling, Statistics, Battery, Network, Storage and This Mac share a quieter translucent material. Reduced Transparency and increased contrast use opaque surfaces. The overview brings live cooling status, a fan-speed gauge, thermal pressure, sensor count, temperature peaks/averages, and shortcuts to Battery, Network and Storage together.

**Cooling** includes Quiet, Balanced and Performance curve presets. Clicking a preset or loading a saved profile changes the editor; **Apply profile** activates it. Quiet starts at the hardware minimum for lighter workloads and still rises to maximum at high temperatures. All presets retain the heat-boost threshold currently in the editor. Fixed speed also previews each fan’s approximate requested RPM.

Use **My profiles → Save current profile…** to name and save the current editor settings, load a saved profile, or remove it from the local library. Up to 24 uniquely named profiles are stored on this Mac, independently of the last applied startup profile.

**Timed boost** runs maximum cooling for 1, 5, 10, 15 or 30 minutes, then returns control to macOS. It is available in Overview, Cooling and the menu bar. End boost returns immediately; successfully applying another profile replaces the timer. Timed boosts do not replace your editor settings or saved startup profile. The timer uses elapsed wall time, including sleep; after an expired boost, waking returns to Automatic. With wake resumption disabled, waking always leaves cooling to macOS. A rejected restoration stays pending for retry; disconnection retains the existing helper/watchdog recovery behavior. Actual sleep/wake remains untested automatically.

**Automatic switching** (Cooling) applies a profile while a rule holds: an app is open (by bundle ID), the Mac is on battery, it is on the power adapter, or a time window that can span midnight. Each rule stores a copy of the chosen preset, Maximum cooling, Automatic or saved profile. Rules are checked about every three seconds from top to bottom and the first match wins. When no rule matches anymore, Breeze reapplies the profile you last applied yourself (Automatic if you never applied one). Rule changes are not saved as your startup profile. Timed boosts pause switching; when a boost ends, a matching rule takes over again. Heat boost applies to every profile. Up to 24 rules are stored locally.

Thermal history offers 2-, 5- and 10-minute views. The export button saves the selected collected history as CSV: ISO 8601 timestamp, hottest die temperature in °C, fastest fan RPM, and CPU load percentage. Unavailable CPU counters are empty. History stays in memory for this app session unless you explicitly export it.

## Customizable menu widget

Open **Settings → Menu bar widget** to choose **Simple** or **Detailed**, then adjust individual readings and sections. Changes save automatically, update the menu bar immediately, and appear in a live preview. The widget uses a native Liquid Glass shell on macOS 26 and later, standard materials on macOS 14–15, and opaque surfaces with Reduced Transparency or increased contrast. Buttons share Breeze’s action style across the widget and main app: consistent heights, typography, padding and corners, neutral supporting actions, mint primary actions and red destructive actions. The preview renders the same controls with actions suppressed.

Simple shows temperature, fan speed, temperature history, and cooling shortcuts. Detailed adds Bluetooth device batteries, CPU/GPU/memory usage, individual fan speeds and limits, CPU user/system/idle and logical-core activity, 1/5/15-minute load, uptime, memory composition and swap, thermal pressure, expandable raw die sensors, and the top five processes by CPU with memory usage. Each reading and section can be hidden independently, and history can span 2, 5, or 10 minutes. The fixed header and footer remain accessible while long widgets scroll.

Menu-bar readings are configurable separately: temperature, fan RPM, CPU, GPU, and memory percentage. Disable all readings for just the fan icon. GPU percentage is the highest reported utilization among exposed accelerators. Unsupported or stale activity readings show a dash; a confirmed stopped fan shows 0 RPM, and Macs without fans show Fanless. Temperature is the hottest reported die sensor, not an overall Mac health score.

The widget activity reader is independent of the Statistics page and cooling control. It samples every two seconds only when an open widget/preview needs CPU details, memory details, processes or GPU, or when GPU is pinned in the menu bar. Processes are enumerated only while an open widget/preview includes Top processes. Closing these views stops unneeded activity collection; the existing lightweight cooling/system monitor continues. Preview cooling actions are disabled.

## Battery

Open **Battery** for charge percentage, charging/plugged-in status, estimated runtime or time until full, cycle count, reported condition and maximum capacity, design/full/remaining capacity, battery identity/serial/firmware, and battery temperature, voltage, current, and power where available. Health and identity come from local System Information and refresh once a minute. When macOS does not report maximum capacity, an explicitly labeled estimate uses nominal capacity (falling back to full charge capacity) divided by design capacity and can differ from System Settings. Positive battery power means charging; negative means discharging. macOS time estimates vary with workload and may take time to become available.

When external power is connected, charger details include its reported wattage, name, manufacturer, voltage/current, model or adapter ID, serial number, and firmware when macOS supplies them. Adapter ratings describe available output, not live wall consumption or battery charging speed. A plugged-in battery can be full or held below full without actively charging; Breeze reports those states separately without guessing the cause. Unsupported details show **Unavailable**, and desktop Macs show a no-battery state. Readings use local IOKit APIs without the cooling helper and refresh every five seconds while Battery is open. Launch with `--battery` to open this page directly.

**Power flow** separates live power from the adapter from battery charge/discharge power. **Idle · 0.0 W** means no net power is flowing through the battery; the adapter can still power the Mac. On supported Macs, input power, voltage, and current come from `AppleSmartBattery`'s `PowerTelemetryData` (`SystemPowerIn`, `SystemVoltageIn`, and `SystemCurrentIn`, converted from milli-units). This is DC power entering the Mac, including charging when active, and excludes charger conversion losses. These registry fields can vary by model or macOS version; unsupported input telemetry shows **Unavailable**, and disconnected adapters never retain a stale input reading. The charger’s reported power rating is shown separately.

### Charge limit

**Battery → Charge limit** stops charging at a chosen level (50–100%, default 80%) through the approved helper, which writes the firmware's charge-inhibit key (`CHTE` on current firmware, `CH0B`/`CH0C` on older firmware) and verifies each readback. The Mac keeps running on adapter power while charging is paused. **Sailing range** (0–20%) waits for the battery to fall that far below the limit before charging resumes, avoiding constant top-ups. **Heat protection** pauses charging while the battery is at or above a chosen temperature (30–45°C) and resumes after it cools by 2°C; it works with or without the limit. Click **Apply** to start, change or stop the limiter.

The helper checks the battery about every five seconds while a Breeze control session is connected; turning the limiter on connects to the helper if needed. Charging is re-enabled whenever the session ends: quitting Breeze, **Disconnect helper**, a lost connection, a heartbeat timeout or a helper error. A restart also clears the firmware setting. Sleep keeps the current charging state. A missing battery reading always allows charging, and a rejected charging write turns the limiter off and re-enables charging. Charge limiting needs the same one-time helper approval as fan control and works on fanless Macs.

### Bluetooth devices

Battery shows charge levels for connected Bluetooth devices that report them, including left/right/case levels for AirPods, from `system_profiler SPBluetoothDataType`. Logitech mice and keyboards (for example MX Master and MX Keys) report battery through Logitech's HID++ protocol instead; Breeze sends read-only HID++ feature queries (unified battery 0x1004, or battery status 0x1000) to Logitech's vendor collection, directly for Bluetooth LE devices and to device slots 1–6 on Unifying/Bolt receivers. macOS counts opening any HID device, mice included, as Input Monitoring, so Breeze never opens a Logitech device until that access is granted. Instead, Battery explains in plain language why the permission is needed and what Breeze reads (only battery level and device name, never typing, clicks or movement), and the system prompt appears only after the user chooses Continue. "Not now" hides the card and leaves a button to bring it back. If notifications are already allowed, Breeze posts one notification the first time it finds such a device; clicking it opens Battery. Breeze never asks for notification permission for this. The widget's Devices section shows a link to the same explanation. Levels refresh once a minute while Battery or a widget with the Devices section is open. Many third-party devices don't report a level. Desktop Macs show this section below the no-battery notice.

## Checkup

**Checkup** reviews the Mac in one pass and changes nothing: thermal pressure and the hottest die, fan behavior under heat, battery condition/health/temperature, whether a charge limit is set, startup disk free space, SSD SMART status/endurance/media errors, rebuildable cleanup space from the last cleanup scan, memory pressure and swap, uptime, cooling-helper setup, and one TCP check to Cloudflare when Internet checks are enabled. Results are sorted Issue → Attention → Tip → Good, with a shortcut to the relevant page. **Copy report** and **Save…** produce a Markdown summary. Battery health below 80% is reported as an issue to match Apple's service guidance. Launch with `--checkup` to open this page directly.

## Alerts

**Settings → Alerts** sends local notifications when the hottest die stays at or above a limit for 30 seconds, the startup disk has less than a chosen amount free, the battery reaches a temperature, the startup SSD's estimated endurance falls to a percentage, or no usable network path exists for 30 seconds (with a follow-up when the connection returns). Each alert fires once, re-arms after its condition clears, and repeats at most every 30 minutes. Temperature is checked every second, disk space and battery every minute, SSD wear every six hours, and connectivity through `NWPathMonitor` without network traffic. macOS asks for notification permission when the first alert is enabled. Alerts need the packaged app and run while Breeze is open.

## Desktop widgets

The packaged app includes a WidgetKit extension (`Contents/PlugIns/BreezeWidgets.appex`) with small and medium **Breeze** widgets: hottest die temperature, fastest fan, cooling status, and in the medium size CPU, memory, battery and free space on the startup disk. Breeze writes a small status file into a team-prefixed app group container about once a minute while it runs, and asks WidgetKit to reload at most every 15 minutes; macOS budgets widget reloads, so values can lag. Each widget shows its reading time and dims after ten minutes without an update. Like Xcode-built extensions, the extension binary uses `_NSExtensionMain` as its entry point; WidgetKit then loads the `@main` widget bundle. The extension is sandboxed and reads only that file. Add the widget from the desktop's **Edit Widgets** after launching Breeze from `/Applications` at least once.

`scripts/build.sh` reads the team ID from the signature, writes the group (`<TEAM>.local.breeze.fancontrol`) into both Info.plists as `BreezeAppGroup`, and signs the extension with App Sandbox and the app with the matching app-group entitlement. If the widget doesn't appear in the gallery, run `pluginkit -m -i local.breeze.fancontrol.widgets` to check registration.

## This Mac

Open **This Mac** for the Mac’s processor and CPU core breakdown, installed memory, graphics and GPU cores, mounted local disks, connected displays, model identifier, model year, serial number, and uptime. The Mac picture and model year come from macOS’s model catalog; hardware readings come from local System Information, IOKit, and system APIs. Unknown details show **Unavailable**. Model year describes the model’s introduction, not the manufacture date of the individual computer. Display resolution is the current mode’s pixel resolution; variable refresh displays show **up to** their supported refresh rate. Refresh reloads the readings, display changes update automatically, and uptime updates every minute. Uptime includes sleep and measures elapsed time since the last restart. Launch with `--this-mac` to open this page directly.

## Network

Open **Network → Activity** for live download/upload rates, positive traffic traces over two or five minutes, and 64-bit transfer totals for the active interface since its last reset. These include local transfers and are not lifetime internet usage. Connection details include interface name, link status, connection type, physical address, Wi-Fi standard/security/channel/band/width, signal and noise, negotiated link speed, local IPv4/IPv6, subnet mask, gateway and system DNS servers. Unsupported readings show a dash. macOS can require Location Services to disclose the Wi-Fi name; **Allow Wi-Fi name** requests that access without collecting coordinates.

**Internet speed test → Start test** runs Apple’s built-in `networkQuality` tool on the active interface. It measures simultaneous download and upload in Mbps and idle latency when available, usually in about 30 seconds. It uses significant internet data and can briefly slow other activity. Cancel stops the test; leaving Network, disabling Internet checks or switching connections also cancels it. Failed and incomplete tests show an error rather than a speed.

With **Internet checks** enabled, Breeze measures TCP handshakes to Cloudflare (`1.1.1.1:443`) approximately every five seconds. A ribbon holds up to 120 actual probe results (roughly ten minutes); uncollected slots stay empty. Jitter is the mean absolute change between consecutive successful round trips over the last twelve probes. A failed probe may indicate a blocked endpoint, not necessarily a complete outage. Once per minute, an ephemeral HTTPS request to `https://1.1.1.1/cdn-cgi/trace` reads the public IPv4 and approximate country. VPNs and proxies can affect results. Toggle Internet checks off to stop these external checks. Monitoring and checks run only while the Network section is open; they do not use the cooling helper.

Open **Network → Apps** for per-process download and upload rates and totals. Breeze reads them from macOS's network statistics (the source behind `nettop` and Activity Monitor) from launch, whether or not the page is open: about every five seconds in the background and every second while the tab is visible, at about 1% CPU. Totals include connections that closed between reads, so short transfers and peer-to-peer apps with many short connections are counted in full. Traffic from before Breeze opened is not included. The Download and Upload columns show the current rate above that direction's total, so a finished upload stays visible. Rows are sorted by combined total and show the app icon and name when the process belongs to a running app, otherwise the process name and PID; helper processes appear separately and exited processes keep their totals. Traffic includes local and loopback transfers. Totals can be reset and are not saved.

Open **Network → Devices → Scan devices** to discover local neighbors. The scan combines an interface-bound ICMP echo sweep, TCP port 80 responses (including connection refusals), macOS ARP records, and Bonjour service advertisements. iPhones and iPads often advertise only `_remotepairing._tcp`, which Breeze browses to learn their host names. Each advertised service is resolved once per scan (up to 512). Models come from AirPlay `model`, RAOP `am`, companion-link `rpMd` or device-info TXT records. A device that advertises nothing and uses a locally administered MAC address is listed as a **Private Wi-Fi device**: phones, tablets, watches and newer laptops use these addresses, so this is a hint rather than an identification. Android phones generally advertise no local services and appear this way. It sends no application requests or credentials to discovered devices. Up to 24 addresses are checked concurrently; a scan listens for names for at least twelve seconds and can be stopped. Only private/link-local IPv4 subnets are swept. Large LANs are limited to this Mac's /24 for active probing, with the real subnet boundaries preserved; neighbor records and Bonjour can add devices from the wider subnet. Public-address, IPv6-only and VPN interfaces are not actively swept. Switching networks clears the inventory, and leaving Network cancels discovery.

The device list shows names, IP/MAC addresses, inferred categories and whether a device responded or only appeared in the neighbor table. Inspect a row for advertised services, model/manufacturer when supplied, discovery evidence, and the observation time. Private MAC addresses are identified as such; Breeze does not claim an unknown manufacturer or exact device model. Device names can be customized locally. Client isolation, sleeping devices, blocked probes and missing advertisements can make the list incomplete; it is not the router's authoritative client list. Bonjour covers workstation, SMB, SSH, AirPlay/RAOP, Google Cast, IPP/IPPS, HTTP, HomeKit, Apple companion/mobile and remote-pairing services. DNS-SD resolves host addresses and TXT records without requiring the device to accept a TCP connection; separate Apple device-info TXT records can supply models. Advertised names and models distinguish iPhones, iPads, Macs, Apple TVs and HomePods. A mobile or remote-pairing service alone is labeled Apple mobile device; a private MAC alone yields only the Private Wi-Fi device hint, never a specific type. If an iPhone does not advertise an identity, unlock it and scan again, or save a local name in device details.

On macOS 15 and later, allow **Local Network** access when prompted by the first scan. If blocked, open **System Settings → Privacy & Security → Local Network**, allow Breeze and scan again. Location Services are optional and separate. No administrator access or network-scanning tools are required. The packaged app declares its local-network purpose and Bonjour services and uses the same stable Apple signing identity as the cooling app. `--network` opens directly to Network for a scripted launch.

## Storage explorer

Open **Storage → Disk overview** for mounted local volumes, capacity, read/write history, and drive health. Select a volume in the rail to inspect it. Activity is sampled every two seconds with 30-second and two-minute views; device metadata refreshes every 30 seconds. Device details expand to show the model, connection, mount point, APFS container, encryption, write access, driver-session transfers, media errors and unsafe shutdowns. NVMe SMART readings include estimated endurance remaining, temperature, spare capacity, lifetime transfers, power-on hours and cycles where the device exposes them. Unsupported readings are explicitly unavailable. Activity covers the whole physical device, so volumes on that device share its readings; APFS volumes may also share capacity, which is never summed across volumes. Multi-device volumes do not inherit a single drive's health or activity. Monitoring uses local macOS APIs and read-only `diskutil info`; no elevated helper or third-party tools are needed. Polling stops when leaving Storage.

Use **Files & cleanup → Choose folder** to select a personal folder. Scanning runs off the main actor and can be cancelled while cooling continues. A resizable sidebar window keeps Overview, Cooling, Statistics, Storage and Settings available.

- **Browse files:** readable rows show file thumbnails, sizes and shares of the current folder. Click a folder to open it or a file to preview its contents. Video and audio use a dedicated native player with playback, seeking and volume controls; other files use Quick Look. Unsupported media shows an error and an option to open the default app. Folder contents and summary totals are indexed off the UI thread. Row thumbnails share a bounded cache and a three-request queue, with offscreen requests cancelled immediately. Breadcrumbs let you return to any parent inside the scan. **Show space map** expands the proportional size map; its 100 largest children appear individually and the rest share a rectangle. All items, including empty files, remain available in the paginated list. Folder colors follow their largest file's category.
- **Duplicates:** non-empty files are grouped by size, filtered by a 64 KB prefix hash, and checked with a full streaming SHA-256 hash. File browsing and previews become available as soon as folder enumeration finishes, while duplicate checking continues; cleanup stays unavailable until those checks finish. Filenames are irrelevant. File identity, size and modification time are checked before and after reading. Matching contents do not imply matching metadata or resource forks. Hard links are counted once, not suggested as extra copies.
- **Worth reviewing:** installers/disk images unchanged for 30+ days, files of at least 100 MB unchanged for 180+ days, and any file of at least 1 GB. These are review cues, not proof that a file is unused. Breeze does not track file or app usage.
- **Cleanup:** files start unselected. Review shows thumbnails and an embedded file preview with the full path before a separate Move to Trash action. Select each review row to inspect it. At least one scanned copy of every duplicate group must stay; retained copies are rechecked before cleanup. Changed, moved, missing or replaced files block validation. Individual move failures are reported. Successful moves update totals and duplicate groups in place, preserving the current folder, tab and list depth. Empty folders stay open, and failed moves stay selected for retry. Rescanning the same root also preserves the folder being explored. Use Finder to restore files from Trash. Breeze never empties Trash.

Scanning excludes hidden entries, symbolic links, system paths, any `Library` directory, app/package contents, iCloud-managed items, dataless placeholders and other mounted filesystems. OS permissions still apply. Unreadable locations and failed duplicate checks are reported. Scans stop at 250,000 files and explicitly mark results partial; use a smaller folder to continue. Excluded data means the map does not represent whole-disk usage. Map and duplicate totals use logical file sizes; APFS clones, compression, snapshots and Trash can make actual recovered space smaller. No elevated helper or Full Disk Access is needed for the supported personal-folder workflow.

For a local fixture or scripted launch, the packaged app also accepts `--scan-folder /absolute/path/to/folder`. It follows the same exclusions and starts no cleanup automatically.

### Storage → Cleanup & apps

The **Cleanup & apps** workspace follows **Scan → Choose → Review → Finish**. **Find cleanup items** reads inventory without selecting or removing anything. A dedicated progress workspace shows what is being checked and offers cancellation. The Choose workspace starts with **Rebuildable** files, groups results by type, and keeps **Everything**, **In use**, and **Selected** views available. Search names, projects and paths, filter recovery risk, and open any row for full details. **Select rebuildable** explicitly adds available, nonpermanent rebuildable items across categories; it excludes applications, leftovers, personal data and in-use items. Individual in-use items remain selectable so their blockers can be resolved during review. Rescans preserve available choices and a cancelled refresh leaves earlier choices visible until a new scan completes.

- **Developer tools:** known disposable subdirectories for npm, pnpm, Yarn, Bun, Homebrew, CocoaPods, SwiftPM, Cargo/rustup, Gradle, Maven, pip/uv/Conda, Go, NuGet, Dart/Flutter, nvm/Volta, Playwright/Puppeteer/Cypress, Android, JetBrains, VS Code/Cursor/Windsurf, Claude and Codex. Shared stores and data that might contain locally published artifacts require review. Credentials, assistant conversations, installed toolchains and source checkouts are not generic cleanup targets.
- **Projects:** per-project `node_modules`, `.next`, `.nuxt`, `.turbo`, `Pods`, Swift `.build`, Rust/Maven `target`, Python virtual environments/bytecode, Flutter/Dart and Gradle build data. Recognition uses project markers rather than arbitrary folder names. Default discovery roots are existing `~/Developer`, `~/Projects`, `~/Code` and `~/Desktop/projects`; **Project folders…** adds or removes roots inside the home folder for this app session. Modification dates are evidence of changes, not a last-worked timestamp.
- **Xcode:** DerivedData, device support, release archives, individual simulator devices, and supported runtime-image inventories. Archives and device data are personal data. Simulator deletion uses `simctl` with the exact reviewed ID; runtime deletion requires all simulators shut down. Unsupported runtime inventories are reported in scan notes and can be managed in Xcode Settings. Breeze never manually removes system runtime directories.
- **Android emulators:** virtual device folders grouped with their `.ini` registrations, plus individual system images by API, variant and architecture. Device names and image references come from bounded configuration metadata. Image details list matching devices and explain the reinstall cost; removing a device includes its test data and snapshots. Standard locations and inherited `ANDROID_AVD_HOME`, `ANDROID_USER_HOME`, `ANDROID_HOME` and `ANDROID_SDK_ROOT` are supported within the home folder.
- **Downloaded installers and duplicates:** scans up to 25,000 files under Downloads for regular `.dmg`, `.pkg` and `.iso` files and duplicates verified with full SHA-256 content hashes. Duplicate entries contain only excess copies and reserve one copy outside the removal inventory. The preserved copy and excess copies are validated again before removal. That preserved copy cannot also be selected as an installer. Packages, linked/cloud files and excluded folders retain the personal scanner's protections; partial results appear in scan notes. Installer age alone does not establish that installation is finished.
- **AI models:** individual Ollama manifests with exclusively referenced blobs, Hugging Face cached repositories, and LM Studio model files in standard locations. Ollama's shared blobs stay in place and are excluded from removable sizes. Removing several models together can retain orphaned shared blobs; remaining models can be rescanned between cleanups. Custom `OLLAMA_MODELS`, `HF_HOME` and `HF_HUB_CACHE` locations inherited by Breeze are supported only inside the home folder. Other custom model paths are not discovered automatically.
- **Applications:** app bundles in `/Applications` and `~/Applications`, reported Spotlight last-use dates when available, per-app caches/logs, exact bundle-ID support data, preferences, saved state and containers. Exact product-name support folders are marked as possible matches for inspection. Related data remains separately selectable; **Select app & related files** prepares a selection for the same cleanup plan. Shared Group Containers, Keychain items, privileged helpers, subscriptions and system apps are outside this uninstaller's scope. Possible leftovers are clearly labeled: an absent app in the scanned install folders does not prove its files are unused.
- **Docker:** individual images and immutable, reclaimable build-cache records from the current local Unix-socket context. The context, endpoint, built-in builder and object IDs are pinned and checked again before removal. Custom/remote builders are excluded. No forced image removal, broad prune, container deletion or volume cleanup is used. Shared layer sizes are upper estimates, and Docker can refuse images still referenced by containers or multiple tags.

**Review selection** opens a full-page cleanup plan. Files and app bundles appear under **Move to Trash**; Docker and simulator operations appear separately under **Remove permanently**, with an explicit acknowledgement. Recovery advice stays visible and paths, purpose and context expand under **What’s included**. Every item has a **Keep** action. Breeze never empties Trash, and estimates are not reported as guaranteed recovered disk space.

The plan checks running apps and known tool processes before enabling removal. Blocking processes appear in the plan with their commands, exact PIDs and the affected cleanup items. Use **Keep these items for later** to continue with the rest, or save work, choose processes, and use **Stop selected & refresh**. Apps receive a normal Quit request and command-line tools receive SIGTERM; Breeze never force quits. Name matches can serve multiple projects. Breeze protects itself and its launching ancestors, rechecks process identity and ownership, reports processes that stay running, and offers Activity Monitor. It refreshes the reviewed items and returns to the plan for another approval. A simulator that stays booted must be shut down in Simulator before refreshing. Stopping a process never starts removal.

Cleanup shows measured item progress and can be stopped. A persistent Finish workspace lists completed items, files or folders moved to Trash, permanent tool removals, and any failures or partial work. **Open Trash** provides a recovery route. Results refresh in the background while the receipt stays visible; remaining items can be reviewed again once that scan completes. Cancellation and partial failures do not hide completed changes. Actual free space can differ because of APFS sharing, snapshots and tool-managed storage.

The cleanup scanner runs off the UI thread, checks complete metadata fingerprints before moving files, rejects linked cleanup roots and ancestors, never follows interior symbolic links, and excludes cloud-only files, other mounted filesystems and special files. Running GUI app ownership is rechecked before removal; known build/tool process names are also checked for the relevant cache. Stop any remaining background tasks before cleanup. Each measured item is limited to 250,000 filesystem entries; project discovery is limited to 100,000 folders and 24 levels per root. Inaccessible, unsupported or changing locations appear in **Scan notes**. Cleanup uses the current user's permissions without the cooling helper or administrator escalation; optional Full Disk Access can expose otherwise hidden Library locations.

The app has been built and packaged. Runtime testing and UI verification are left to the user per the project instructions.

### AI cleanup assistance with your existing tools

**Storage → Cleanup & apps → Ask AI** connects the cleanup inventory to your own Codex, Claude Code, or another local MCP client. Breeze makes no model API calls, requires no model API key, and does not read or reuse the assistants' credentials. To use subscription access, sign into the official AI tool with an eligible account; that tool's current usage limits and billing apply. A locally running CLI can still send metadata to cloud models. See the official [Codex authentication documentation](https://learn.chatgpt.com/docs/auth?surface=cli) and [Claude Code authentication documentation](https://code.claude.com/docs/en/authentication).

The packaged app includes **BreezeMCP**, a standalone MCP stdio executable, built and signed by `scripts/build.sh`. It requires neither Node nor Python. Rebuild the app after updating the sources so this executable is included. The AI assistant sheet also works with a development build when `BreezeMCP` is built beside the `Breeze` executable.

1. Run **Find cleanup items**, then click **Ask AI**. Breeze detects an installed Codex or Claude Code and starts analysis immediately, with no setup sheet. It prefers your saved assistant when installed, otherwise the first supported installed client. The button names the assistant it will use (for example **Ask Claude Code**); its arrow switches between Codex and Claude Code, and the choice is remembered. The same choice and the metadata-sharing switch are also in **Settings → AI assistant**. The official CLI must already be signed in. Breeze finds common Homebrew, local-bin, npm, Volta and nvm installations and the bundled Codex executable without starting a shell.
2. Optionally expand **AI priorities** on the cleanup screen to enter a target and exclusions, such as “Reclaim roughly 30 GB; keep my local models and current iOS projects.” The sliders button opens **AI options** for a preferred assistant, sharing, response details and manual connections. A saved sharing-off preference is respected and explained inline.
3. The assistant sees opportunities grouped by kind, including Android/iOS devices, runtimes and images, Downloads installers, verified excess duplicate copies, rebuildable output, downloadable tools/models and apps with recorded last use over 90 days ago. The prompt asks for substantial space and concrete recovery/data-loss tradeoffs rather than restricting recommendations to rebuildable caches. Missing activity dates never count as proof of inactivity. A device may be proposed as an optional sacrifice, with its data-loss cost explained.
4. The proposal arrives on the cleanup screen under **Review suggestions**. Read the per-item reasons and use **Keep** to exclude anything. Items in use can be proposed when their app/process blocker is resolvable during review. Only the removal button in Breeze starts cleanup; permanent tool actions retain their separate acknowledgement.

The run shows progress and a **Stop analysis** button on the cleanup screen. Requests time out after ten minutes. Stopping, disabling sharing, rescanning, starting cleanup, or quitting cancels the session; each background MCP connection is pinned to its scan ID so it cannot use a replacement scan. A cancelled request's late proposal cannot be applied to the new scan. Completion and missing CLI, authentication and connection failures appear inline; the captured assistant response is available in **AI options**, including when it recommends no cleanup. This uses the official [Codex non-interactive mode](https://developers.openai.com/codex/noninteractive/) and [Claude Code programmatic CLI](https://code.claude.com/docs/en/headless).

Breeze launches the CLI directly with argument arrays and a private temporary working directory. It passes the prompt through a private input file and bounds captured output. Temporary session files are removed when the process finishes. The one-shot connection does not register an MCP server globally or edit CLI settings. Codex runs with a read-only sandbox, shell execution and web search disabled, and user configuration ignored for this run; Claude Code has built-in tools disabled and only the supplied Breeze MCP connection. Both retain their official CLI login handling. Breeze removes inherited model API key variables from the child environment rather than falling back to those keys. Existing CLI account billing and usage limits still apply.

**Manual connection and copy options** keeps the existing workflow for your own assistant session. Choose **Other MCP client** to copy the server configuration and merge it into that client's configuration. For an app installed in `/Applications`, equivalent manual setup commands are:


```sh
codex mcp add breeze -- '/Applications/Breeze.app/Contents/MacOS/BreezeMCP'
claude mcp add --transport stdio --scope user breeze -- '/Applications/Breeze.app/Contents/MacOS/BreezeMCP'
```

These manual commands configure the chosen AI tool; Breeze only copies them. The connection follows the official [Codex MCP setup](https://developers.openai.com/codex/mcp/) and [Claude Code MCP setup](https://code.claude.com/docs/en/mcp). Moving the app requires updating a manually registered connection; Ask AI always uses the current executable location. **Copy prompt for assistant** remains available for external sessions. **Copy compact scan summary** is a manual alternative without MCP: it copies category totals and up to three candidates per opportunity kind, at most 21 items, for pasting into any assistant.

If Codex lists `breeze` but reports that it failed to connect, registration succeeded but the MCP handshake did not. Rebuild with `zsh scripts/build.sh` to replace the packaged executable, then restart the assistant session so it starts the updated server. BreezeMCP reads incoming pipe data as it arrives; older builds could wait for a full input buffer and stall initialization. If you moved Breeze, run the setup command again with its current path. Sharing a scan is required for cleanup tool calls, but not for connecting or listing tools.

The MCP interface has four tools:

| Tool | Behavior |
| --- | --- |
| `cleanup_summary` | Returns the current snapshot ID, scan age, expiry, category totals, permission caveats, up to three candidates per opportunity kind and up to eight rebuildable suggestions. |
| `list_items` | Returns compact records, largest first, filtered by scope/category/query. Defaults to opportunities across risk levels; `suggested` retains the rebuildable-only view and `all` exposes the full inventory. Defaults to 15 items, at most 40, with `nextOffset` pagination. |
| `inspect_items` | Returns richer metadata for up to eight IDs, with a response budget and `remainingIDs` when more requests are needed. |
| `propose_cleanup` | Saves a proposal of 1–200 unique, reviewable item IDs and their reasons, including permanent/device tradeoffs and blockers that can be handled in review. It cannot select items, clean files, run shell commands, or empty Trash. |

List, inspect, and proposal calls require the current `snapshotID`. Rescanning generates new IDs and rejects older proposals. The server reads only the shared snapshot; it does not scan arbitrary folders or accept filesystem paths as cleanup targets. Breeze maps the opaque IDs back to the live inventory and reuses its existing file-change, running-process, and tool checks before removal. A proposal never silently merges with a manually selected cleanup. Pending proposals are checked every two seconds while the cleanup workspace is visible, or when **Check for proposal** is clicked.

Cleanup metadata now includes root creation/modification/access dates, Spotlight last-opened dates where supplied, the newest change anywhere in a measured tree, file/link and folder counts, owning-app last use, known process names to stop, purpose, recovery implications, and existing Xcode/project context. The detail view displays the dates and counts too. An owning app's last-use date is distinct from a cache's own last-opened date. Missing values mean unknown. Spotlight last use covers LaunchServices opens, and filesystem access dates can reflect background activity; neither is a complete usage history or a reason to remove data by itself. See Apple's [last-used metadata](https://developer.apple.com/documentation/coreservices/kmditemlastuseddate) and [creation date](https://developer.apple.com/documentation/foundation/urlresourcekey/creationdatekey) documentation.

Sharing is enabled by default. The user's toggle choice is saved across launches; only changing the toggle changes this preference. Each successful cleanup scan publishes fresh metadata while enabled. Expiry, scan cancellation, and publishing failures do not switch the preference off. The private bridge uses `~/Library/Application Support/Breeze/CleanupAssistant/` (directory mode `0700`, files `0600`) and contains metadata plus one pending proposal, with home-directory prefixes shortened to `~`, bounded strings/context, and no file contents. Snapshots expire four hours after the scan. Turning sharing off, starting cleanup, changing project folders, and normal app exit revoke the snapshot; rescanning replaces it when sharing is enabled. A crash can leave an expired file on disk, but the MCP server rejects expired snapshots and the next launch removes previous sharing files. A fresh scan is needed after relaunch. Previously supplied metadata can remain in the assistant's conversation. The toggle controls the Breeze connection; it does not constrain any other filesystem or shell tools the user has separately granted to their assistant.

Runtime testing and UI verification are left to the user under `AGENTS.md`.

## One-time helper setup

In Breeze, open **Settings → Cooling helper → Set up cooling helper**. Approve Breeze in **System Settings → General → Login Items & Extensions**, then apply your cooling profile. macOS may request administrator authentication for that initial approval. Later app launches, reconnects, and fan changes reuse the approved helper, including after a restart. Revoking approval, removing the helper, changing the signing identity, or some macOS security changes can require setup again.

The helper starts on demand and leaves fan control with macOS while Breeze is disconnected. **Open Breeze at login** is a separate, optional setting. To revoke access, use **Remove helper** in Breeze or disable its background item in System Settings. For reliable availability before login, keep the packaged app in `/Applications`; moving or deleting it can make the service unavailable.

## Cooling profiles

- **Maximum cooling:** one click requests each fan's hardware-reported maximum RPM.
- **Fixed speed:** percentages span each fan's own RPM range. 0% means the reported minimum, with a 1200 RPM floor where possible; it never deliberately stops a fan.
- **Custom curve:** edit 2–12 temperature/speed points. Breeze interpolates between them. Temperatures must strictly increase and fan speeds must stay level or rise. Balanced and Performance presets provide starting points.
- **Target temperature:** a feedback controller adjusts fan demand using the hottest die reading, temperature error, accumulated error, and the rate of heating. It increases cooling immediately and reduces demand by at most two percentage points per second. A temperature target is an aim: sufficiently heavy workloads can exceed it even at maximum fan speed.
- **Automatic:** explicitly hands fan control back to macOS.

Choose a mode, edit its values, and click **Apply profile**. Applying or selecting Maximum cooling connects to the approved background helper if necessary. First use requires the one-time setup above. The last successfully applied profile is saved locally.

## Heat behavior

The original 90°C release-to-automatic cutoff has been removed. Heat never causes Breeze to release a working override. Instead, the controller requests 100% when the configurable boost threshold is reached (default 90°C), system thermal pressure becomes serious/critical, or die readings disappear. Boost holds until temperature falls at least 3°C below the threshold. A fixed 100% request stays at 100% through that transition.

This does not disable Apple's thermal protections or change the fan's maximum rating. Firmware can still reject or change an override. The app reports a firmware disagreement or restoration failure explicitly instead of describing a temperature cutoff as macOS taking over.

## Wake and startup

**Settings → Resume the active cooling profile after wake** is enabled by default. Breeze pauses overrides for sleep but retains its authenticated local connection and root helper while the app is alive. On wake it reapplies the last active profile. Turning this option off leaves cooling with macOS after wake.

Optional settings apply the saved profile when the app opens and register Breeze using Apple's **Open at login** service. The registered helper retains its approval across app sessions. Passwords are never stored. Actual whole-machine sleep/wake has not been tested automatically because that would interrupt the user's running workloads.

## Statistics

Open **Statistics** for five resource tabs:

- **CPU:** user/system/idle utilization, history, load per logical core, 1/5/15-minute load averages, and core counts. CPU load is normalized to 0–100% across the whole processor; cores use their macOS logical indices.
- **GPU:** each exposed accelerator, its core count when available, device/renderer/tiler utilization with separate histories, and GPU power and average active frequency. These driver registry counters vary by Mac and macOS release. System-wide FPS and Neural Engine utilization are not collected; unsupported counters show unavailable rather than zero.
- **Power & frequency (CPU tab):** whole-Mac power from the SMC (`PSTR`), GPU power from IOReport's Energy Model, and the average active frequency and active residency of the efficiency and performance clusters from IOReport DVFS residency. Frequency tables come from the `pmgr` registry entry (Hz on M1–M3, kHz on later chips; Breeze detects the scale). Recent macOS releases report CPU, Neural Engine and DRAM energy as exactly zero to unprivileged processes, so Breeze treats zero as withheld and reads those channels in the root helper while a control session is connected (**Connect helper** starts one without changing cooling). The chart shows CPU power when available and whole-Mac power otherwise. The Neural Engine is shown as power because macOS doesn't expose its utilization. Readings need two samples and show unavailable on Macs without these counters.
- **Memory:** app, wired, compressed and available memory, cached files, system memory pressure, allocated/used swap, and memory/swap histories. Available memory includes reclaimable caches. Accounting and sampling can differ from Activity Monitor.
- **Processes:** an Activity Monitor-style table of accessible processes with name, CPU, memory, threads, PID, owner and CPU time. Click column headings to sort, search by name/user/PID, or filter to your processes. CPU uses elapsed-time deltas; 100% means one fully used core, so a process can exceed 100%. The first sample warms up CPU counters. Memory prefers physical footprint, falling back to resident size. Protected readings use a dash, and macOS may hide some protected processes. Selecting a row shows its identity and a button to open Activity Monitor for further inspection.
- **Thermal:** CPU/GPU die sensors, system thermal pressure, fan readings, five-minute temperature/fan histories, and raw sensor keys. Sensor keys vary by chip; labels are based on AppleSMC key families.

The activity reader samples every two seconds while Statistics is open, independently of cooling control. Process enumeration runs only on the Processes tab. Pause freezes readings; Resume starts a new CPU baseline. Choose a 2-, 5- or 10-minute history; up to ten minutes stays in memory for this session, and gaps remain unfilled. No root helper, external service or disk log is used for activity collection. `--statistics` opens CPU statistics; `--processes` opens the process table.


## Helper lifecycle

The UI is unprivileged. The macOS Service Management daemon accepts only typed fan/profile/lifecycle commands through a launchd-owned Unix socket in `/var/run`. It authenticates clients using the socket’s audit token, the exact Breeze signing identifier, and an Apple signature from its own signing team; unsigned apps and other identifiers are rejected. The UI checks that the socket peer is root. It also checks peer UID and PID, validates profiles and RPM bounds, verifies firmware readback, and allows only one Breeze control session. Curve and target updates run in the helper, independent of which UI page is open.

Automatic fan mode is restored on quit, disconnect, a six-second heartbeat timeout while awake, or a control error. Charging is re-enabled whenever a session that limited it ends; charging errors never release an active cooling profile. Sleep is an explicit paused state, allowing the helper to remain authorized without holding a manual fan override. Restoration failures are reported and retried on disconnect. Helper errors go to the unified log: `log show --predicate 'subsystem == "local.breeze.fancontrol.helper"' --last 1h`. Software fallback cannot guarantee restoration if the root helper itself is forcibly killed or the firmware fails. Fanless Macs monitor only. Do not enable fan control in another utility at the same time.

The helper is bundled at `Contents/MacOS/BreezeHelper`, with its service property list in `Contents/Library/LaunchDaemons`. `SMAppService` manages registration, approval, launch on demand, and removal. No password is cached, and no setuid tool or kernel extension is installed. Local builds use Apple Development signing; distributed releases must be notarized. macOS approval must be verified interactively on the target Mac.

## Validation

```sh
swift test
zsh scripts/verify-helper-transport.sh
dist/Breeze.app/Contents/MacOS/BreezeHelper --status
```

Automated tests cover charge-limit hysteresis, heat protection and missing battery readings, Bluetooth battery parsing, switching-rule matching and persistence, number encodings, invalid RPM targets, delayed writes, bounded retries, curve validation/interpolation, target-controller response, boost hysteresis, sensor-loss behavior, high-temperature 100% requests, watchdog deadlines, profile persistence encoding and sleep/wake command encoding. Cleanup tests cover the preserved duplicate copy, files changed since the scan, linked cleanup roots and ancestors, blocked items, and AI proposals for stale, unknown or duplicate IDs; they exercise only failure paths, so nothing reaches the Trash. They do not change hardware settings or sleep the machine. The transport fixture launches separate signed processes and confirms that Breeze is accepted while an unrelated signing identifier, an ad-hoc copy, and an invalid requested identifier are rejected. It requires access to the signing keychain and local sockets.

Earlier live reads detected two fans (1499–5348 and 1499–5776 RPM). A subsequent live read confirmed both in manual mode with maximum targets and actual speeds above 5300 RPM. The new curve/target modes require live validation. Broad model compatibility is unverified.
